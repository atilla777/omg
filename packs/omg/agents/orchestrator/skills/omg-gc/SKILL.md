# OMG Gas City / Beads operations

Use the decomposition procedure below from `omg-decompose` only after confirming the work breakdown. Launch only an explicitly authorized `omg-probe` or `omg-development` source, or observe a workflow without launching. Other source types have no formula.

## Select and inspect

- From the city context use `gc rig list --json` to obtain the registered rig name, absolute project path and Beads state. Do not treat the city/HQ rig as the project by default. Confirm the chosen path is the project root. Use `bd -C <rig-path>` for **every** Beads operation; never let cwd implicitly select the city's Beads database.
- Check `bd -C <rig-path> config get types.custom` before creation. The three OMG source types are `omg-research`, `omg-development` and `omg-bugfix`. If a required type is missing, ask the user before changing rig configuration; if authorized, append only missing values to the existing comma-separated `types.custom` (preserve Gas City service types and any other custom types), then read it back. A missing type must not be replaced by a built-in `task` type. If Beads is uninitialized or the rig is not writable, stop and report it; do not initialize or attach a rig implicitly.
- Before creating, inspect existing issues in the **selected rig** (`bd -C <rig-path> list --all --limit 0 --json`, `bd -C <rig-path> show <id> --json` as needed) for the same specification path and epic. Do not equate an empty default `bd list` or its first page with no prior work. If the state is ambiguous, ask the user before changing it.

## Persist the confirmed graph

Use `bd -C <rig-path> create '<epic title>' --type epic --description '<purpose and rig-relative docs/requirements/...md reference>' --acceptance '<epic completion criteria>' --silent` and capture its returned ID. For each approved subtask use `bd -C <rig-path> create '<title>' --type <omg-type> --parent <epic-id> --description '<scope and rig-relative spec reference>' --acceptance '<observable criteria>' --silent`. Pass user content safely as arguments or a body file, never interpolate it into a shell command. Retain the temporary-label-to-Beads-ID map.

Once all subtasks exist, for each confirmed prerequisite add `bd -C <rig-path> dep add <dependent-id> <prerequisite-id>` (default `blocks`: the first issue is blocked by the second). Do not create a blocking edge from a child to the epic; `--parent` supplies hierarchy. If any write fails, stop and report the partial graph for deliberate reconciliation, rather than recreating it. During decomposition never invoke `gc sling`, `gc formula cook`, `gc route`, `bd ready` as a dispatch trigger, or any execution command.

Read back the epic and each child with `bd -C <rig-path> show <id> --json`, and blocking edges with `bd -C <rig-path> dep list <id> --type blocks --json`. Confirm children have the intended parent, type, requirements reference and acceptance criteria, and that the edge direction matches the confirmed plan. Present actual IDs and relationships, not just CLI success messages.

## Manual launch

- Establish the city and selected rig with `gc rig list --json` and obtain the **existing source bead ID** from the user or an unambiguous lookup in that rig. Do not interpret an epic ID as a subtask or infer consent from a previously created bead. An epic launch means first show eligible children and ask which individual ready source bead(s) to launch. A status request needs no permission to launch.
- Read `bd -C <rig-path> show <source-id> --json` and `bd -C <rig-path> dep list <source-id> --type blocks --json`. Require an open, ready source with no open blocking prerequisites. Select exactly `omg-probe → omg-probe` or `omg-development → omg-development`; `omg-research`, `omg-bugfix`, epics and other types have no supported formula. Show the unsupported type or missing formula; do not guess a fallback. Before asking for explicit development launch authorization, explain that the whole method includes a direct origin/main push and source closure after review. Do not interpret consent to create tasks or review as consent to launch this formula.
- Before routing, use the observation procedure below to discover **all** earlier roots for this source, including closed/failed ones. If there is a live root, stop and show it. If there is a previous terminal root, show its outcome and ask how to handle it; do not silently start a second run. Check `gc --city <city> --rig <rig-name> formula show <formula>` and `gc --city <city> agent list` for the formula and its targets (`omg.probe-worker` for probe; `omg.plan-worker`, `omg.build-worker`, `omg.review-worker`, `omg.publish-worker` for development). If any are missing, stop. For development, confirm the selected rig has an accessible `origin/main` and the project main worktree can be fast-forwarded before starting. Never call `gc formula cook --attach` for this action.
- After the user explicitly approves this source's launch, call `gc --city <city> --rig <rig-name> sling omg.orchestrator <source-id> --on <formula> --var source_id=<source-id> --json` **once**, without `--force`, `--no-formula` or `drain`. The `--rig` flag is essential: the workflow belongs in the source rig's store. If a concurrent run wins, surface the `already has live workflow(s)` error and read the existing workflow, never retry with force. Report `workflow_id` from JSON and confirm its root's `gc.formula_name`, `gc.input_convoy_id` and `gc.var.source_id` before claiming success. Inspect actual steps and sessions rather than inferring execution success from sling. Probe never publishes; development publication and source closure require explicit step evidence, not a successful sling or review alone.
- If the inspect step is ready but no `omg.probe-worker` session appears after dispatch, create one with `gc --city <city> session new omg.probe-worker --no-attach --json`. If a worker session already exists, inspect its current work; submit to it only if idle, or queue a follow-up when it finishes another probe. Submit a message to the chosen session ID: `gc --city <city> session submit <session-id> 'Claim and complete only the routed omg-probe steps for source <source-id> in rig <rig-name>. Resolve the rig path and use bd -C for every Beads command. After each step, claim the next ready step for this workflow; stop if none is ready or another workflow is claimed.'` (use `--intent follow_up` if busy). Never create a second session if one is already working; if startup or submission fails, show the unresolved step and failure rather than saying execution is underway. The user has already authorized this one diagnostic run. If a step stays open after the worker finishes, show it and the session state; do not launch another formula.
- For development, after dispatch inspect actual ready steps and sessions. For ready `prepare` or `plan` use `omg.plan-worker`, for `implement`, `document` or `apply-fixes` use `omg.build-worker`, for `review` or `synthesize-review` use `omg.review-worker`, for `publish` use `omg.publish-worker`. Only already-started legacy workflows may also have `finalize` (`omg.build-worker`) and `close-source` (`omg.publish-worker`). If the target has no session, create one using `gc --city <city> session new <target> --no-attach --json`; verify it is active before submitting (a startup-time `agent_not_ready` is not a successful handoff). Inspect an existing session before reuse and never start a second session for a busy target; submit to an idle session (or `--intent follow_up` for a busy session) with selected rig and source ID, requesting `gc hook --claim --json`, the named step skill, and only steps belonging to this workflow. Recheck Beads after each stage and after controller check; the next review attempt is spawned by Gas City, never by the agent or a second sling. If a handoff does not occur, show the pending step and session state. Report success only after verifying the remote commit, source closure and workflow root; on stale main/push failure leave source and publish step open, do not force-push or sling again.

## Restore a workflow overview by source ID

Use **fresh Beads and Gas City data**, not chat history. The source bead has no direct workflow ID. All commands below use the chosen rig; never search the city Beads store in its place.

1. Read the source: `bd -C <rig-path> show <source-id> --json`. Query all issues, including closed and infrastructure rows: `bd -C <rig-path> list --all --include-infra --limit 0 --json`. Find convoy issues whose `tracks` dependency points to the **exact** source ID (the `input convoy for ...` title alone is insufficient). If no matching convoy, report no linked workflow; if partial metadata or unreadable store, report uncertainty rather than assuming no run.
2. Find all roots with `metadata.gc.kind = workflow` and `metadata.gc.input_convoy_id` equal to one of those convoy IDs. Read each root with `bd -C <rig-path> show <root-id> --json`; verify its `gc.var.source_id` is the source ID and its formula is the expected one. If multiple roots match, list all of them and do not choose an arbitrary one. Include failed/closed roots. A stray `gc.execution_routed_to` on the source alone is **not** proof of a workflow.
3. For each root, collect **all** issues whose `metadata.gc.root_bead_id` equals its ID (including generated control beads); read each with `bd show --json` as needed for notes, `gc.outcome`, `gc.failure_reason`, `gc.final_disposition`, blockers and routing. Distinguish the workflow root, the work steps (`gc.step_id`), and the generated `workflow-finalize` control. Show each step ID, status, blocker and failure/notes. For `gc.session_name` and `gc.routed_to`, consult `gc --city <city> session list --state all --json` and `gc --city <city> session peek <session-id>` when needed. Match an actual session ID/template/target before reporting it as waiting for the user; an open step alone is not proof of a waiting Herdr session. If no active session is visible, say so and show the unresolved step/error; do not invent a notification or restart a formula.
4. Present rig, source ID/type/status, formula, input convoy ID, root ID/status/outcome, work and control step IDs/statuses, real session state, failures or uncertainty. For development, include recorded worktree/artifact paths, `review-loop` attempt number and max, child IDs with `gc.attempt`, current check verdict, publish status and SHA in `origin/main`, and whether the source is actually closed. Do not confuse closed child beads of a failed attempt with approval, or an approved review with publication. For probe, state no publication. If workflow is missing, show that explicitly. Observing never creates a new workflow.
