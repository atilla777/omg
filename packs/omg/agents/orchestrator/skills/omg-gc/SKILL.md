# OMG Gas City / Beads operations

Load `omg-human-dialog` for questions and user-facing results. Use the decomposition procedure below from `omg-decompose` only after confirming the work breakdown. Launch only an explicitly authorized `omg-probe` or `omg-development` source, or observe a workflow without launching. Other source types have no formula.

## Select and inspect

- From the city context use `gc rig list --json` to obtain the registered rig name, absolute project path and Beads state. Do not treat the city/HQ rig as the project by default. Confirm the chosen path is the project root. Use `bd -C <rig-path>` for **every** Beads operation; never let cwd implicitly select the city's Beads database.
- Check `bd -C <rig-path> config get types.custom` before creation. The three OMG source types are `omg-research`, `omg-development` and `omg-bugfix`. If a required type is missing, ask the user before changing rig configuration; if authorized, append only missing values to the existing comma-separated `types.custom` (preserve Gas City service types and any other custom types), then read it back. A missing type must not be replaced by a built-in `task` type. If Beads is uninitialized or the rig is not writable, stop and report it; do not initialize or attach a rig implicitly.
- Before creating, inspect existing issues in the **selected rig** (`bd -C <rig-path> list --all --limit 0 --json`, `bd -C <rig-path> show <id> --json` as needed) for the same specification path and epic. Do not equate an empty default `bd list` or its first page with no prior work. If the state is ambiguous, ask the user before changing it.

## Persist the confirmed graph

Use `bd -C <rig-path> create '<epic title>' --type epic --description '<purpose and rig-relative docs/requirements/...md reference>' --acceptance '<epic completion criteria>' --silent` and capture its returned ID. For each approved subtask use `bd -C <rig-path> create '<title>' --type <omg-type> --parent <epic-id> --description '<scope and rig-relative spec reference>' --acceptance '<observable criteria>' --silent`. Pass user content safely as arguments or a body file, never interpolate it into a shell command. Retain the temporary-label-to-Beads-ID map.

Once all subtasks exist, for each confirmed prerequisite add `bd -C <rig-path> dep add <dependent-id> <prerequisite-id>` (default `blocks`: the first issue is blocked by the second). Do not create a blocking edge from a child to the epic; `--parent` supplies hierarchy. If any write fails, stop and report the partial graph for deliberate reconciliation, rather than recreating it. During decomposition never invoke `gc sling`, `gc formula cook`, `gc route`, `bd ready` as a dispatch trigger, or any execution command.

Read back the epic and each child with `bd -C <rig-path> show <id> --json`, and blocking edges with `bd -C <rig-path> dep list <id> --type blocks --json`. Confirm children have the intended parent, type, requirements reference and acceptance criteria, and that the edge direction matches the confirmed plan. Present actual IDs and relationships, not just CLI success messages.

## Manual launch

- Establish the city and selected rig with `gc rig list --json` and obtain the **existing source bead ID** from the user or an unambiguous lookup in that rig. Do not interpret an epic ID as a subtask or infer consent from a previously created bead. A plain-language epic launch needs a choice of one child; `/omg` instead uses the deterministic selection below. A status request needs no permission to launch.
- For `/omg`, resolve the project rig from explicit arguments or conversation context; if only one non-HQ project rig is plausible, use it. Resolve the plan as a **single existing epic** in that rig linked to a confirmed published `docs/requirements/` specification. If the argument names an epic, verify its parent/type and specification link; otherwise inspect all issues (`bd -C <rig-path> list --all --limit 0 --json` and `show` as needed), select the sole matching epic with open direct children, or ask **one** question to choose among plausible projects/plans. Never infer a plan from chat memory or a draft specification. Read all direct children, including closed ones, and their `blocks` dependencies. Candidates are non-closed children with no open blocking prerequisite, including a child already in progress; sort by Beads creation time ascending, then full ID ascending for ties. The first is the **one** next task. Inspect its previous workflows before deciding whether a new launch is possible: a live run is shown rather than skipped in favor of a later child. For a new launch require `status=open` and confirm the source appears in `bd -C <rig-path> ready --json` (do not treat that list as dispatch); otherwise report its status. If none is unblocked, show blockers/status rather than launch. If the first is of an unsupported type, show it and stop: do not skip it in favor of a later development child or substitute another formula. If multiple rigs/plans cannot be resolved or the next task cannot be identified reliably (missing timestamp/ID, unreadable links or dependencies), ask one selection question and do not launch until resolved. Never launch multiple children per invocation.
- For `/omg-dev`, require exactly one explicit source ID (and unambiguous rig); a missing or ambiguous ID prompts one selection question. For both commands, read `bd -C <rig-path> show <source-id> --json` and `bd -C <rig-path> dep list <source-id> --type blocks --json`; verify type, parent/plan when specified, open state and readiness with no open blocking prerequisites. `/omg` and `/omg-dev` support **only** `omg-development → omg-development`; `omg-research`, `omg-bugfix`, epics, probes and other types must not be launched through them. A separate explicit diagnostic request may use `omg-probe → omg-probe`. Show unsupported type or missing formula; never guess a fallback. For a plain-language development launch, explain beforehand that the method includes direct origin/main push and source closure after review; invoking `/omg` or `/omg-dev` already grants that authorization, so do not ask again.
- Before routing, use the observation procedure below to discover **all** earlier roots for this source, including closed/failed ones, even if the source appears not ready or closed. If there is a live root, stop and show it instead of launching. If a previous root failed or ended without verified publication and closure, show its outcome and ask how to reconcile it; never silently retry. A successfully completed closed source is reported as done, not relaunched. If links or store data are incomplete, stop instead of treating unknown history as no history. Check `gc --city <city> --rig <rig-name> formula show <formula>` and `gc --city <city> agent list` for the formula and its targets (`omg.probe-worker` for probe; `omg.prepare-worker`, `omg.plan-worker`, `omg.build-worker`, `omg.document-worker`, `omg.review-worker`, `omg.publish-worker` for development). If any are missing, stop. For development, confirm the selected rig has an accessible `origin/main` and the project main worktree can be fast-forwarded before starting. Never call `gc formula cook --attach` for this action.
- After authorization (the invocation of `/omg` or `/omg-dev` is sufficient for its one selected source), call `gc --city <city> --rig <rig-name> sling omg.orchestrator <source-id> --on <formula> --var source_id=<source-id> --json` **once**, without `--force`, `--no-formula` or `drain`. Recheck source readiness and prior roots immediately before sling. The `--rig` flag is essential: the workflow belongs in the source rig's store. If a concurrent run wins, surface the `already has live workflow(s)` error and read the existing workflow, never retry with force. Report `workflow_id` from JSON and confirm its root's `gc.formula_name`, `gc.input_convoy_id` and `gc.var.source_id` before claiming success. Inspect actual steps and sessions rather than inferring execution success from sling. Probe never publishes; development publication and source closure require explicit step evidence, not a successful sling or review alone. After this workflow finishes, do not dispatch another child without a new request.
- For the probe inspect/confirm steps, apply **Session isolation before every handoff** below to `omg.probe-worker`. Submit to the selected session ID: `gc --city <city> session submit <session-id> 'Claim and complete only the routed omg-probe steps for source <source-id> under root <root-id> in rig <rig-name>. Resolve the rig path and use bd -C for every Beads command. After each step, claim the next ready step for this workflow; stop if none is ready or another workflow is claimed.'` Use `--intent follow_up` only when that session is busy on the **same** root. If startup or submission fails, show the unresolved step and failure rather than saying execution is underway. The user has already authorized this one diagnostic run. If a step stays open after the worker finishes, show it and the session state; do not launch another formula.
- For development, after dispatch inspect actual ready steps and sessions. Read each ready bead's `gc.run_target` metadata and use that target, verifying it is a known role: in new workflows `prepare` uses `omg.prepare-worker`, `plan` uses `omg.plan-worker`, `implement` and `apply-fixes` use `omg.build-worker`, `document` uses `omg.document-worker`, `review` uses `omg.review-worker`, and `publish` uses `omg.publish-worker`. Already-started workflows may use `omg.plan-worker` for `prepare`, `omg.build-worker` for `document` and `finalize`, `omg.review-worker` for `synthesize-review`, and `omg.publish-worker` for `close-source`. If the metadata is missing or inconsistent, stop rather than guessing a role. Apply **Session isolation before every handoff** below for every role and every step, including each new `review-loop` review or fix attempt. Submit to the selected session ID with rig name, source ID, root ID, named step skill and a request to `gc hook --claim --json` for only this workflow. Use `--intent follow_up` only for busy work on the same root. Recheck Beads after each stage and after controller check; the next review attempt is spawned by Gas City, never by the agent or a second sling. If a handoff does not occur, show the pending step and session state. Report success only after verifying the remote commit, source closure and workflow root; on stale main/push failure leave source and publish step open, do not force-push or sling again.

### Session isolation before every handoff

This applies to probe and **all** development targets, including repeated review/fix steps. Before `session submit`, read the ready step and root in the selected rig (`gc.root_bead_id`, `gc.var.source_id`, `gc.input_convoy_id` and the convoy's `tracks` link); verify they identify the requested root and exact source. Check `gc --city <city> session list --state all --json` for the target template, and inspect the actual candidate session ID and its current/previous claimed step, messages (`gc session peek <session-id>` / logs) and corresponding Beads root. Do not infer ownership from the role name, `active` state or an idle terminal. Record the session's verified rig, source ID and root ID for this handoff; if history is ambiguous, stop and report the pending step instead of guessing.

- If an open session belongs to this **same rig, source and root**, continue its conversation for subsequent steps and attempts. If busy on that root, wait or submit a same-root `--intent follow_up` only; never interrupt it.
- If it belongs to **another** root (even if the source ID happens to match), inspect its claimed work and root/steps. While it is busy or that workflow still has work for this target, do not close, interrupt, reset or enqueue a different task into it. Leave the new step open, report the session and reason, and retry the handoff after it finishes. A finished previous workflow with no outstanding work for the target may be retired with `gc --city <city> session close <old-session-id>`; verify the close response and that its ID no longer appears in `session list --state all --json` (`gc 1.5.0` omits closed sessions there), then create `gc --city <city> session new <target> --no-attach --json`. Closing the GC session removes its live Herdr pane but does not delete its saved OpenCode conversation; retain its OpenCode `session_key` for opening the history later.
- If there is no open session for the target, create one with `gc --city <city> session new <target> --no-attach --json`. Use the **returned ID**, verify its template, active/readiness state and fresh OpenCode conversation before submitting; `agent_not_ready` is not a handoff. If multiple sessions exist and ownership cannot be established, stop and report them; do not choose one arbitrarily. Never reuse a closed session or use `session reset` to erase context.

On failure to close or create a session, or to establish a fresh conversation, leave the step open and report the exact error and session/step IDs for recovery. Re-read session state just before submit to avoid racing another handoff; if ownership changes, stop. Never describe an unsubmitted or queued handoff as completed work.

## Restore a workflow overview by source ID

Use **fresh Beads and Gas City data**, not chat history. The source bead has no direct workflow ID. All commands below use the chosen rig; never search the city Beads store in its place.

1. Read the source: `bd -C <rig-path> show <source-id> --json`. Query all issues, including closed and infrastructure rows: `bd -C <rig-path> list --all --include-infra --limit 0 --json`. Find convoy issues whose `tracks` dependency points to the **exact** source ID (the `input convoy for ...` title alone is insufficient). If no matching convoy, report no linked workflow; if partial metadata or unreadable store, report uncertainty rather than assuming no run.
2. Find all roots with `metadata.gc.kind = workflow` and `metadata.gc.input_convoy_id` equal to one of those convoy IDs. Read each root with `bd -C <rig-path> show <root-id> --json`; verify its `gc.var.source_id` is the source ID and its formula is the expected one. If multiple roots match, list all of them and do not choose an arbitrary one. Include failed/closed roots. A stray `gc.execution_routed_to` on the source alone is **not** proof of a workflow.
3. For each root, collect **all** issues whose `metadata.gc.root_bead_id` equals its ID (including generated control beads); read each with `bd show --json` as needed for notes, `gc.outcome`, `gc.failure_reason`, `gc.final_disposition`, blockers and routing. Distinguish the workflow root, the work steps (`gc.step_id`), and the generated `workflow-finalize` control. Show each step ID, status, blocker and failure/notes. For `gc.session_name` and `gc.routed_to`, consult `gc --city <city> session list --state all --json` and `gc --city <city> session peek <session-id>` when needed. Match an actual session ID/template/target before reporting it as waiting for the user; an open step alone is not proof of a waiting Herdr session. If no active session is visible, say so and show the unresolved step/error; do not invent a notification or restart a formula.
4. Present rig, source ID/type/status, formula, input convoy ID, root ID/status/outcome, work and control step IDs/statuses, real session state, failures or uncertainty. For development, include recorded worktree/artifact paths, `review-loop` attempt number and max, child IDs with `gc.attempt`, current check verdict, publish status and SHA in `origin/main`, and whether the source is actually closed. Do not confuse closed child beads of a failed attempt with approval, or an approved review with publication. For probe, state no publication. If workflow is missing, show that explicitly. Observing never creates a new workflow.

## Epic completion after source closure

When observing an epic or a closed source with a parent epic, load the shared `omg-human-dialog` skill and show the epic's actual status separately from each source and workflow. After a newly closed development source, the publish worker runs `assets/checks/omg-close-epic.py` from the imported pack. If it could not finish (including a stopped session after source closure), resume safely with `python3 <pack-root>/assets/checks/omg-close-epic.py --rig <absolute-rig-path> --source <closed-source-id>`; the script verifies the selected rig, all direct children and publication evidence anew, and never pushes or starts a workflow. It is safe to rerun for an open epic or an already closed one. Never treat a closed `omg-development` bead alone as proof of publication. If the JSON result is `blocked`, report its reason and leave the epic open; do not force-close it or infer completion from Beads' child statuses. A status request for an open source remains read-only.

## Report the outcome

After decomposition, launch, observation, or a stopped/partial operation, give a human-facing report using the shape in the shared `omg-human-dialog` skill and, if accessible, `assets/reports/gc-result.md`. State **what was done**, **current state**, and **what to do next**; summarize decisive evidence in plain language, then include exact IDs and paths needed for recovery. For decomposition, separate created tasks from execution and name the next separately authorized action. For launch, separate accepted dispatch from completed steps, review, publication and closure; give the next checkpoint or the actual pending session/step. For observation, state whether work exists, where it is waiting and who can act. If nothing was changed or a command failed midway, say so, identify verified partial writes, and propose only a safe next step. Do not present a recommendation to start a new run as authorization to do so. When a decision is required, ask only one question with numbered answers and a brief recommendation.
