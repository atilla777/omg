# Review one attempt

Load `omg-dev-context` and `omg-dev-review-attempt` and follow both shared contracts before reading or writing an attempt artifact. When asking the human or reporting a blocked step in Herdr, load `omg-human-dialog` and follow its question and result rules.

Claim the assigned review bead. Read the original source bead, its acceptance criteria and linked rig requirements, and the closed prepare/plan/implement/document beads for this root. Follow their recorded paths to the prepared context, technical plan, `test-results.md` and `documentation-result.md`; verify identities and actual contents rather than relying on bead summaries. Inspect the task worktree's actual changes, including untracked files and deletions, and the relevant surrounding code and tests. Do not edit the implementation or documentation.

Review along two explicit axes, using the **selected rig's** sources rather than OMG's own project rules:

1. **Task requirements:** Map each source criterion and applicable linked requirement to the changed behavior, tests and documentation. Compare the result with the agreed scope and technical plan; flag missing, incorrect or out-of-scope behavior. The plan is evidence of intent, not permission to override the source criteria or rig requirements.
2. **Project standards and verification:** Read applicable rig instructions (`AGENTS.md`, scoped rules, contributor guidance), project review requirements, architecture and conventions for the changed files. Check that implementation and tests follow those rules, including required test coverage, relevant test/lint commands and documentation checks. Compare changed files and tests with the commands, scope, observed outcomes, environment and caveats recorded in `test-results.md` and `documentation-result.md`; verify that required checks actually passed and cover the affected behavior. Run a focused check if the evidence is insufficient and it is safe and appropriate in this worktree, recording the command and observed result; do not infer a pass from a claim in a summary. Do not rerun every check merely to duplicate valid evidence.

For each actionable finding, cite the violated criterion or rig rule (or the specific missing evidence), point to a concrete rig-relative file/location, command or producer artifact, explain the impact and the smallest required correction. Distinguish required fixes from optional suggestions; use `required_fixes` only for required findings and do not introduce new requirements from general heuristics. If a source criterion and a project rule conflict, or a human decision is necessary to proceed, record the question and use `blocked` until the human answers in Herdr. Missing or failed required checks and correctable gaps in implementation/evidence require `changes_required`, not approval. Approve only when both axes pass for the current worktree and no required finding remains; do not claim verification that was not performed.

For direct review → fix write `review/attempt-<gc.attempt>/review.json` with `schema: omg.review.v2`; for an existing synthesis attempt use `omg.review.v1` (synthesis supplies `required_fixes`). Include integer `attempt`, `source_id`, `workflow_root_id`, `review_step_id`, `verdict: approved|changes_required|blocked`, and `findings` (unique stable per-attempt IDs, severity, rig-relative affected files and actionable descriptions). For v2 also include `required_fixes`: actionable items with nonempty `finding_ids` referencing findings, descriptions and rig-relative affected files; `changes_required` needs at least one, `approved` needs neither findings nor required fixes.

For roots with `omg.workspace.artifacts_root`, create `review/attempt-<gc.attempt>/` inside that validated directory and write `review.md` **in the same attempt directory** as `review.json`; include `markdown_report_path` (worktree-relative path of `review.md`) and `reviewed_files` in the JSON. Inventory `git -C <worktree> ls-files -m -o -d --exclude-standard -z`, record exactly these rig-relative paths with SHA-256 of each regular file (null for deletions), reject symlinks and unrelated changes. The map is a snapshot of **everything** reviewed for publication.

In `review.md`, separately summarize the task-requirements and project-standards/verification conclusions, criterion/rule coverage, evidence and any limits; explain each verdict and finding for this source/root/attempt without duplicating large prose in the bead. Older roots without that metadata write only `review.json` in their prepared directory; put the same concise rationale in the available review artifact and bead notes. Record the exact JSON path as bead `omg.review.report_path` and, when written, the Markdown path as `omg.review.markdown_path`. Read files and metadata back.

On `blocked`, record the reason and question on the review bead, leave it open in Herdr until the human answers: closing it would let gc 1.5.0 advance the iteration. For direct v2 review, after verifying the report and its identity set `omg.review.schema=omg.review.v2`, `omg.review.verdict` to exactly `approved` or `changes_required`, and `gc.outcome=pass` on this bead. **Before closing**, read the bead back and require its root and positive attempt to match the assigned review-loop, its `gc.step_ref` to end with `review-loop.iteration.<attempt>.review`, its recorded report path to resolve to the verified report, its schema and verdict to match that report, and `gc.outcome=pass`; require exactly one review bead for this root/attempt. If any value is missing, ambiguous or inconsistent, record the reason and leave this bead open for repair. The runtime check reads the recorded schema and verdict, not the report contents. Already-started v1 synthesis workflows are not supported by the current checker: leave their review bead open and report that manual handling is required; do not close it under the old contract.
