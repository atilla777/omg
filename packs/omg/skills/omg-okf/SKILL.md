# Durable project documentation in OKF v0.2

Use this skill when **writing** durable documentation under the selected rig's `docs/`, including feature specifications. The rig root and permission to write come from the calling skill; do not write to the city working directory. This skill governs the document format, not agreement with the user, workflow evidence, or publication. Do not apply it to `.omg/tasks/` artifacts or already-started workflows' operational `docs/tasks/<source-id>/` artifacts.

Follow the [Google OKF v0.2 specification](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md). Treat the rig's `docs/` directory as the OKF bundle for documents written by OMG. Do not claim the entire existing directory conforms until its files have been checked; do not migrate untouched files just to adopt OKF.

1. Read the existing document and nearby project conventions before changing it. Preserve valid content, project-specific headings, links and unknown frontmatter fields. Convert a pre-OKF file to OKF when editing it; do not change unrelated files. For feature specifications, keep the agreed goal, scope and acceptance criteria sections required by `omg-requirements`.
2. A regular concept document is UTF-8 Markdown beginning with parseable YAML frontmatter delimited by `---` lines. Set a non-empty, descriptive `type` (for example `Feature Specification` for a feature specification); add `title` and a one-sentence `description` where useful. Keep the remainder standard Markdown. `type` is the only always-required field; do not invent a mandatory taxonomy, headings, tags, resource URI, timestamp or extra metadata. Preserve meaningful project-specific frontmatter and body structure.
3. `index.md` and `log.md` are reserved at every directory level: do not use them as concept documents. If editing an OKF index, keep it as a directory listing; only the bundle-root `docs/index.md` may have frontmatter, limited to `okf_version: "0.2"`. A log has no frontmatter and uses date headings `## YYYY-MM-DD`, newest first. Do not create an index or log merely to write a concept. If an existing reserved file serves a different project purpose, do not silently overwrite or convert it: raise the conflict with the calling skill/user.
4. Use ordinary Markdown links for relationships between documents. Prefer relative links that work in the project's repository; OKF also supports bundle-root-relative links when suitable for the consumer. Check links to local targets before claiming success. Preserve `generated`, `verified`, `sources`, `status`, `stale_after` and other optional v0.2 fields when accurate, and update them only when their meaning is actually satisfied. Never invent a human verification event, actor, source, timestamp or freshness guarantee. When changing content, do not retain an obsolete `verified` assertion as if it applied to new text.
5. Read the written file back: verify its frontmatter parses, its `type` is non-empty (for concepts), its Markdown body retains the agreed content, and changed local links resolve. Check the relevant repository documentation checks and report the result to the calling skill. A format failure blocks claiming the documentation update complete.

For example, a new `docs/requirements/search.md` can begin with `---`, `type: Feature Specification`, `title: Поиск`, `description: Требования к поиску в проекте.`, `---`, followed by `# Поиск`, `## Цель`, `## Границы`, and `## Критерии приёмки`. For an existing `docs/api.md` without frontmatter, keep its API details and add a suitable `type` (such as `API Reference`) while updating its changed content. Do not turn either document into an operational report or silently assert `verified` merely because the agent edited it.
