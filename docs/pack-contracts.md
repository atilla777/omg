# Начальные контракты OMG (PLAN-007)

Этот документ определяет интерфейсы для следующих задач на основе [требований](workflow-requirements.md), [архитектуры скиллов](skill-architecture.md) и [пробы Gas City](gas-city-probe.md). В `packs/omg/` есть роль входа, скиллы требований и декомпозиции, а также диагностическая формула ручного запуска. Методы выполнения реальных задач ещё не реализованы.

## Типы и выбор метода

Для *исходных* подзадач зарезервированы пользовательские типы Beads `omg-research` (исследование), `omg-development` (разработка), `omg-bugfix` (исправление бага). Это значения поля `type`, а не формулы. Их нужно добавлять к существующим `types.custom` конкретного rig, сохраняя служебные типы Gas City. Пока нет проверенной формулы ни для одного из них, все три типа **не поддерживаются для запуска**. Отдельно для диагностики поддерживается `omg-probe → omg-probe`, не создаваемый обычной декомпозицией. Наличие пользовательского типа само по себе не разрешает `gc sling` и не выбирает встроенную формулу. При неизвестном типе или отсутствующей формуле оркестратор сообщает причину и запрашивает решение.

## Ответственность и поставка

- Городской агент `orchestrator` — диалог с пользователем в OpenCode через Herdr, определение намерения и границ действия; его постоянный промпт не содержит методик шагов.
- Диагностический `probe-worker` читает исходный bead и закрывает только собственные шаги, не изменяя проект. Роли исполнителей реальных задач появятся вместе с их формулами. Исполнитель получает назначенный bead шага и ссылку на исходную подзадачу, пользуется явно названной процедурой и передаёт проверяемый результат; он не выбирает за пользователя следующий этап и не публикует результат без согласованного шага публикации. Ревью и исправление разделены по [требованиям](workflow-requirements.md#метод-выполнения-подзадачи-разработки).
- `omg-orchestrator` направляет разговор к `omg-requirements` для согласования и поиска требований, к `omg-decompose` для отдельно подтверждённой декомпозиции и к `omg-gc` для операций Beads и разрешённого запуска диагностического типа с обзором. Скиллы исполнения реальной работы добавляются отдельно. Импортируется `packs/omg/`, скиллы лежат в каталоге роли и должны быть видны ей в OpenCode; установки скиллов в самостоятельный OpenCode не требуется.
- Pack объявляет городскую роль и именованную сессию; конкретная city задаёт `[providers.opencode] base = "builtin:opencode"` и `[session] provider = "herdr"`. Роль использует транспорт `tmux`, поскольку ACP встроенного OpenCode не появился в Herdr в [пробе](gas-city-probe.md#наблюдения-и-ограничения). Город и rig создаются и подключаются отдельно; pack не создаёт rig и не изменяет настройки Beads автоматически.

Для локальной проверки до коммита добавить в `pack.toml` отдельной city импорт `[imports.omg]` с `source = "<абсолютный путь>/packs/omg"`, затем выполнить `gc --city <city> import check`. `gc import add <путь-в-Git-worktree>` превращает путь в `file://`-импорт **из HEAD** и до коммита новых файлов pack не находит; после публикации использовать опубликованный Git-источник и зафиксированную версию вместо локального пути. Для пробы city создаётся вне OMG через `gc init --template minimal --default-provider codex --no-start <city>`, а rig подключается через `gc --city <city> rig add <rig> --name trial --prefix trial --start-suspended`. В `city.toml` пробной city нужно указать `workspace.provider = "opencode"`, `[providers.opencode] base = "builtin:opencode"` и `[session] provider = "herdr"`; встроенная роль `mayor` минимального шаблона не относится к OMG.

## Разговорные требования (PLAN-008)

Разговорный вход (PLAN-008) использует `gc rig list --json` для выбора проекта, не подменяя rig городским рабочим каталогом оркестратора. Согласованная спецификация фичи сохраняется в `docs/requirements/<slug>.md` внутри выбранного rig после подтверждения пользователем. Поиск в этом каталоге и чтение файла восстанавливают контекст в следующем диалоге; сохранение не создаёт Beads и не запускает формулу. Если rig или документ неоднозначны, агент уточняет выбор.

## Декомпозиция (PLAN-009)

После подтверждения отдельного плана декомпозиции из сохранённой спецификации `docs/requirements/<slug>.md` создаётся исходный bead `epic`, его дочерние подзадачи с одним из трёх OMG-типов, критериями приёмки и ссылкой на относительный путь спецификации в описании каждой задачи. `--parent` задаёт иерархию; `bd dep add <dependent> <prerequisite>` задаёт только подтверждённые блокирующие связи между подзадачами. Перед записью проверяется отсутствие существующей декомпозиции; при частичном сбое возвращаются уже созданные ID, без повторного создания. Поддержка типов проверяется в `types.custom` выбранного rig; добавление недостающих типов требует отдельного разрешения и сохраняет уже настроенные значения. После записи эпик, дети и зависимости перечитываются из Beads. Создание задач не вызывает `gc sling` и не выбирает формулу. Операции описаны в скиллах `omg-decompose` и `omg-gc` внутри pack.

## Ручной запуск и обзор (PLAN-010)

Только для существующего bead типа `omg-probe` после явного разрешения: `gc --city <city> --rig <rig> sling omg.orchestrator <source-id> --on omg-probe --var source_id=<source-id> --json`. Оркестратор проверяет готовность, тип, наличие формулы и предыдущих workflow, не использует `--force` и не запускает повторно при обнаружении корня. Это диагностическая формула из двух последовательных read-only шагов с отдельным агентом `omg.probe-worker`; если готовый шаг остаётся без сессии, оркестратор создаёт её и передаёт работу worker через `gc session submit`, затем проверяет фактическое выполнение. Статус исходного bead и исход корня проверяются отдельно: завершение пробного workflow не гарантирует закрытия исходной задачи. Публикации нет. Декомпозиция по-прежнему создаёт только три типа реальной работы.

Обзор строится по точной цепочке `source-id → tracks входного convoy → gc.input_convoy_id корня → gc.root_bead_id шагов`, включая закрытые и ошибочные записи. Статусы и метаданные Beads сопоставляются с `gc session list --state all --json`; ожидание ответа сообщается только при наличии свидетельства реальной сессии. Процедура описана в [скилле `omg-gc`](../packs/omg/agents/orchestrator/skills/omg-gc/SKILL.md).

## Контекст шагов будущей формулы

Минимальный контракт каждого шага: на входе — ID исходной подзадачи, её `type`, ссылка на требования (если есть), идентификатор корня workflow, ссылки на результаты предшественников и назначение шага; на выходе — статус, ссылка на проверяемый артефакт или свидетельство, замечания/причина остановки и контекст для следующего шага. Для разработки подготовительный шаг один раз разрешает ID исходной подзадачи в ветку, worktree и каталог артефактов и сохраняет полученные пути для следующих шагов. ID служебного bead или входного convoy не подменяет исходный ID. Конкретные имена артефактов, способ передачи между worktree и критерии переходов определяются с первой формулой; этот каркас их не исполняет.

Для восстановления после смены диалога отправная точка — сохранённые требования в `docs/` rig и ID исходного bead. Для запущенной подзадачи связь восстанавливается по членству исходного bead во входном convoy, `gc.input_convoy_id` на корне workflow и шагам корня; у исходного bead нет прямого ID workflow в проверенной версии Gas City. Ручной диагностический запуск проверяет прежние корни и не использует низкоуровневый `cook --attach`, который не обеспечивает идемпотентность. При остановке шага результат и причина должны оставаться доступны по исходному ID. Процедура обзора диагностической формулы приведена выше; её пригодность для формул реальной работы предстоит проверить отдельно.

## Проверка каркаса — 6 октября 2026

На отдельной city `omg-plan007-city` и приостановленном rig `trial` вне OMG (`gc 1.5.0`, `herdr 0.8.2`) `gc lint packs/omg` и `gc import check` прошли. `gc skill list --agent omg.orchestrator` показал скилл роли. `gc start --dry-run` показал каноническую сессию `omg.orchestrator`; после запуска снимок Herdr показал её терминал. Из рабочего каталога роли `opencode debug skill` обнаружил `omg-orchestrator`, а реальный запрос через `gc session submit omg.orchestrator` вызвал `Skill "omg-orchestrator"` и вернул `omg-entrypoint-ready` в `gc session peek`. Пробная city остановлена и снята с регистрации; созданный для проверки supervisor удалён, состояние systemd linger возвращено к `no`.

Проба PLAN-007 подтверждает доступность **входного каркаса**; проверка действия пользователя и сохранения контекста выполнена отдельно в PLAN-008. Исходные задачи, формулы, роли исполнителей и передачу артефактов в PLAN-007 не запускали.
