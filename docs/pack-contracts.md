# Начальные контракты OMG (PLAN-007)

Этот документ определяет интерфейсы на основе [требований](workflow-requirements.md), [архитектуры скиллов](skill-architecture.md) и [пробы Gas City](gas-city-probe.md). В `packs/omg/` есть роль входа, скиллы требований и декомпозиции, диагностическая формула и метод разработки с публикацией одной подзадачи после ревью.

## Типы и выбор метода

Для *исходных* подзадач зарезервированы пользовательские типы Beads `omg-research` (исследование), `omg-development` (разработка), `omg-bugfix` (исправление бага). Это значения поля `type`, а не формулы. Их нужно добавлять к существующим `types.custom` конкретного rig, сохраняя служебные типы Gas City. Ручные сопоставления: `omg-development → omg-development` (разработка, ревью и прямая публикация), `omg-probe → omg-probe` (диагностика, не создаётся обычной декомпозицией). Исследование и исправление бага **не поддерживаются для запуска**. Наличие пользовательского типа само по себе не разрешает `gc sling` и не выбирает встроенную формулу. При неизвестном типе или отсутствии формулы оркестратор сообщает причину и запрашивает решение.

## Ответственность и поставка

- Городской агент `orchestrator` — диалог с пользователем в OpenCode через Herdr, определение намерения и границ действия; его постоянный промпт не содержит методик шагов.
- Диагностический `probe-worker` читает исходный bead и закрывает только собственные шаги, не изменяя проект. `plan-worker` готовит worktree и технический план, `build-worker` реализует с тестами, обновляет документацию, отдельно исправляет замечания и подводит итог. `review-worker` проверяет результат и синтезирует замечания, не меняя код. `publish-worker` проверяет snapshot, публикует без force и отдельно подтверждает SHA до закрытия исходного bead. Исполнитель получает назначенный bead шага и ссылку на исходную подзадачу, пользуется явно названной процедурой и передаёт проверяемый результат; не выбирает за пользователя следующий этап. Ревью и исправление разделены по [требованиям](workflow-requirements.md#метод-выполнения-подзадачи-разработки).
- `omg-orchestrator` направляет разговор к `omg-requirements` для согласования и поиска требований, к `omg-decompose` для отдельно подтверждённой декомпозиции и к `omg-gc` для операций Beads, разрешённого запуска и обзора. Скиллы шагов разработки лежат у соответствующих ролей. Импортируется `packs/omg/`; установки скиллов в самостоятельный OpenCode не требуется.
- Pack объявляет городскую роль и именованную сессию; конкретная city задаёт `[providers.opencode] base = "builtin:opencode"` и `[session] provider = "herdr"`. Роль использует транспорт `tmux`, поскольку ACP встроенного OpenCode не появился в Herdr в [пробе](gas-city-probe.md#наблюдения-и-ограничения). Город и rig создаются и подключаются отдельно; pack не создаёт rig и не изменяет настройки Beads автоматически.

Для локальной проверки до коммита добавить в `pack.toml` отдельной city импорт `[imports.omg]` с `source = "<абсолютный путь>/packs/omg"`, затем выполнить `gc --city <city> import check`. `gc import add <путь-в-Git-worktree>` превращает путь в `file://`-импорт **из HEAD** и до коммита новых файлов pack не находит; после публикации использовать опубликованный Git-источник и зафиксированную версию вместо локального пути. Для пробы city создаётся вне OMG через `gc init --template minimal --default-provider codex --no-start <city>`, а rig подключается через `gc --city <city> rig add <rig> --name trial --prefix trial --start-suspended`. В `city.toml` пробной city нужно указать `workspace.provider = "opencode"`, `[providers.opencode] base = "builtin:opencode"` и `[session] provider = "herdr"`; встроенная роль `mayor` минимального шаблона не относится к OMG.

## Разговорные требования (PLAN-008)

Разговорный вход (PLAN-008) использует `gc rig list --json` для выбора проекта, не подменяя rig городским рабочим каталогом оркестратора. Согласованная спецификация фичи сохраняется в `docs/requirements/<slug>.md` внутри выбранного rig после подтверждения пользователем. Поиск в этом каталоге и чтение файла восстанавливают контекст в следующем диалоге; сохранение не создаёт Beads и не запускает формулу. Если rig или документ неоднозначны, агент уточняет выбор.

## Декомпозиция (PLAN-009)

После подтверждения отдельного плана декомпозиции из сохранённой спецификации `docs/requirements/<slug>.md` создаётся исходный bead `epic`, его дочерние подзадачи с одним из трёх OMG-типов, критериями приёмки и ссылкой на относительный путь спецификации в описании каждой задачи. `--parent` задаёт иерархию; `bd dep add <dependent> <prerequisite>` задаёт только подтверждённые блокирующие связи между подзадачами. Перед записью проверяется отсутствие существующей декомпозиции; при частичном сбое возвращаются уже созданные ID, без повторного создания. Поддержка типов проверяется в `types.custom` выбранного rig; добавление недостающих типов требует отдельного разрешения и сохраняет уже настроенные значения. После записи эпик, дети и зависимости перечитываются из Beads. Создание задач не вызывает `gc sling` и не выбирает формулу. Операции описаны в скиллах `omg-decompose` и `omg-gc` внутри pack.

## Ручной запуск и обзор (PLAN-010)

Только для существующего bead типа `omg-probe` после явного разрешения: `gc --city <city> --rig <rig> sling omg.orchestrator <source-id> --on omg-probe --var source_id=<source-id> --json`. Оркестратор проверяет готовность, тип, наличие формулы и предыдущих workflow, не использует `--force` и не запускает повторно при обнаружении корня. Это диагностическая формула из двух последовательных read-only шагов с отдельным агентом `omg.probe-worker`; если готовый шаг остаётся без сессии, оркестратор создаёт её и передаёт работу worker через `gc session submit`, затем проверяет фактическое выполнение. Статус исходного bead и исход корня проверяются отдельно: завершение пробного workflow не гарантирует закрытия исходной задачи. Публикации нет. Декомпозиция по-прежнему создаёт только три типа реальной работы.

Обзор строится по точной цепочке `source-id → tracks входного convoy → gc.input_convoy_id корня → gc.root_bead_id шагов`, включая закрытые и ошибочные записи. Статусы и метаданные Beads сопоставляются с `gc session list --state all --json`; ожидание ответа сообщается только при наличии свидетельства реальной сессии. Процедура описана в [скилле `omg-gc`](../packs/omg/agents/orchestrator/skills/omg-gc/SKILL.md).

## Контракт контекста шагов

Минимальный контракт каждого шага: на входе — ID исходной подзадачи, её `type`, ссылка на требования (если есть), идентификатор корня workflow, ссылки на результаты предшественников и назначение шага; на выходе — статус, ссылка на проверяемый артефакт или свидетельство, замечания/причина остановки и контекст для следующего шага. Для разработки подготовительный шаг один раз разрешает ID исходной подзадачи в ветку, worktree и каталог артефактов и сохраняет полученные пути для следующих шагов. ID служебного bead или входного convoy не подменяет исходный ID. Конкретные имена и передача для этапов разработки определены ниже; для остальных типов работы контракты предстоит уточнить.

Для восстановления после смены диалога отправная точка — сохранённые требования в `docs/` rig и ID исходного bead. Для запущенной подзадачи связь восстанавливается по членству исходного bead во входном convoy, `gc.input_convoy_id` на корне workflow и шагам корня; у исходного bead нет прямого ID workflow в проверенной версии Gas City. Ручной запуск проверяет прежние корни и не использует низкоуровневый `cook --attach`, который не обеспечивает идемпотентность. При остановке шага результат и причина должны оставаться доступны по исходному ID. На пробном rig PLAN-011 подтверждены общий корень и notes между этапами разработки; восстановление обзора через новый диалог оркестратора для этой формулы отдельно не проверялось.

## Метод разработки (PLAN-011)

После явного разрешения для готовой исходной задачи `omg-development` оркестратор проверяет прежние workflow и вызывает `gc --city <city> --rig <rig> sling omg.orchestrator <source-id> --on omg-development --var source_id=<source-id> --json` без `--force`. Формула v2 создаёт последовательность `prepare → plan → implement → document → review-loop → finalize → publish → close-source` и управляющий `workflow-finalize`; маршрутизация шагов — к `omg.plan-worker`, `omg.build-worker`, `omg.review-worker` и `omg.publish-worker`. Явное разрешение этого метода относится ко всей одной исходной подзадаче, включая push в `origin/main`. Только завершённый корень с подтверждённым `close-source` означает опубликованный результат.

Ключ пространства — ID исходной задачи, проверенный по корню (`gc.var.source_id`), а не ID шага/convoy. Ветка `task/<source-id>`, worktree `<rig-parent>/.omg-worktrees/<rig-directory-name>/<source-id>` и каталог `docs/tasks/<source-id>/` в нём создаются через `gc worktree ensure`, проверяются через `gc worktree verify` с привязкой к source ID, base SHA и workflow root ID как generation. `context.md` фиксирует фактические пути; `implementation-plan.md`, `test-results.md` и `documentation-result.md` фиксируют план, тесты и документацию. Исполнители читают notes предшественников и файлы одного worktree; ID шага не подменяет исходный ID.

После документации `review-loop` с `check.max_attempts = 6` создаёт для каждой попытки отдельные beads `review → synthesize-review → apply-fixes` с `gc.attempt` и `gc.step_ref`. JSON-артефакты `review.json` (`omg.review.v1`), `synthesis.json` (`omg.review-synthesis.v1`) и `fix.json` (`omg.review-fix.v1`) лежат в `docs/tasks/<source-id>/review/attempt-<N>/`. Fix получает synthesis **через блокирующую зависимость своей попытки** (посредством `scope-check`), а не через поиск самого нового файла. Runtime check сопоставляет все три файла с конкретными bead ID, source ID, корнем и попыткой: `changes_required` после исправления и тестов порождает новую попытку, `approved` с no-op открывает `finalize`. Первая реализация не повторяется. Control bead сохраняет `gc.attempt_log`; старые beads остаются закрытыми. `development-result.md` суммирует историю и актуальный результат на момент ревью.

**Ограничение gc 1.5.0:** закрытие synthesis с `gc.outcome=fail` при `blocked` привело в пробе к новой попытке вместо остановки. Согласованная модель: при `blocked` synthesis сохраняет артефакт и причину, остаётся открытым с вопросом человеку; check не срабатывает и новая попытка не создаётся. Это ожидание ответа, **не** терминальное состояние. Незакоммиченные артефакты остаются только в worktree до будущей интеграции.

Официальный [Gas City Build Pack](https://github.com/gastownhall/gascity-packs/tree/main/gascity) использует `do-work.prepare-worktree` для выбора source anchor и передачи `work_dir`, а [`build-basic-review`](https://github.com/gastownhall/gascity-packs/blob/main/gascity/formulas/build-basic-review.formula.toml) — `check` с дочерними review/fix beads. OMG переиспользует механизмы `gc worktree ensure/verify` и v2 check/children, но сохраняет типизированные исходные задачи, одиночный запуск без drain, именованную ветку и `docs/tasks/<source-id>/`. Build Pack не является зависимостью. Подробные процедуры — в скиллах `omg-dev-*`; результаты проверки — в PLAN-011.

## Публикация и завершение (PLAN-012)

После approved review `finalize` записывает переносимые rig-relative ссылки и `publish-manifest.json` со списком и SHA-256 изменённых файлов; абсолютные локальные пути остаются только в Beads, в публикуемых артефактах они запрещены. Отдельный `publish` использует helper pack: сериализует публикации одного Git-репозитория lock-файлом в `.git`, сверяет содержимое с манифестом, локальный и удалённый `main` с подготовленной базой, создаёт один commit на `task/<source-id>`, делает **обычный non-force push HEAD:refs/heads/main**, перечитывает SHA удалённого `main` и fast-forward локального `main`. При сдвиге базы или конфликте параллельных изменений останавливается без переписывания истории: потребуются согласование и повторная проверка результата, а не молчаливое слияние. После подтверждения сохраняет `publication-report.json` в исходном worktree и SHA в метаданных workflow. Если сеть или обновление локального main отказали после удачного push, исходный bead остаётся открытым; повторная проверка не создаёт новый workflow или commit.

Отдельный `close-source` заново проверяет отчёт, наличие commit в `origin/main` и локальном `main` и закрывает **исходный** bead с `gc.outcome=pass` и SHA; лишь после этого закрывается шаг. Закрытие снимает `blocks` с зависимой исходной задачи, которая при подготовке берёт уже опубликованный `main`. Публикация не создаёт PR, не использует `drain` и не запускает зависимую задачу автоматически. Официальный Build Pack разделяет preflight/push и `do-work.close-source-anchor`, но публикует ветки/PR и может закрывать anchor раньше выбранной OMG проверки remote/main; поэтому OMG нужен собственный метод прямой публикации без зависимости от Build Pack.

## Проверка каркаса — 6 октября 2026

На отдельной city `omg-plan007-city` и приостановленном rig `trial` вне OMG (`gc 1.5.0`, `herdr 0.8.2`) `gc lint packs/omg` и `gc import check` прошли. `gc skill list --agent omg.orchestrator` показал скилл роли. `gc start --dry-run` показал каноническую сессию `omg.orchestrator`; после запуска снимок Herdr показал её терминал. Из рабочего каталога роли `opencode debug skill` обнаружил `omg-orchestrator`, а реальный запрос через `gc session submit omg.orchestrator` вызвал `Skill "omg-orchestrator"` и вернул `omg-entrypoint-ready` в `gc session peek`. Пробная city остановлена и снята с регистрации; созданный для проверки supervisor удалён, состояние systemd linger возвращено к `no`.

Проба PLAN-007 подтверждает доступность **входного каркаса**; проверка действия пользователя и сохранения контекста выполнена отдельно в PLAN-008. Исходные задачи, формулы, роли исполнителей и передачу артефактов в PLAN-007 не запускали.
